## 1. Tìm hiểu về CI/CD

### 1.1 Khái niệm CI/CD

**Theo ITviec:** CI là viết tắt của Continuous Integration (tích hợp liên tục), CD là Continuous Delivery (chuyển giao liên tục) hoặc Continuous Deployment (triển khai liên tục). Khái niệm CI/CD thường đề cập đến việc tự động hóa trong quy trình phát triển phần mềm và chuyển giao sản phẩm, giúp việc tích hợp diễn ra nhanh hơn và sản phẩm hoàn thiện được chuyển đến người dùng trong thời gian ngắn nhất.

**Theo Milan:** CI (Continuous Integration) là kỹ thuật thay đổi code được thực hiện đều đặn và tăng dần một cách đáng tin cậy; các bản cập nhật code merge vào repository được đảm bảo tin cậy nhờ quy trình build-and-test tự động mà CI kích hoạt, sau đó code được triển khai nhanh chóng và hiệu quả thông qua quy trình CD. Bài này cũng giải thích CI/CD pipeline là bộ tự động hóa giúp developer chuyển các thay đổi code nhỏ từ máy cá nhân sang môi trường test và production một cách đáng tin cậy, và trước khi CI/CD phổ biến, các đội ngũ hay gặp "integration hell" — làm việc riêng lẻ nhiều tuần/tháng rồi merge code rất đau đớn, deploy thủ công và dễ lỗi.

### 1.2 Quy trình làm việc điển hình theo mô hình CI/CD

**Theo Milan** — 4 giai đoạn cơ bản của một pipeline: (1) Source stage: code được lấy từ hệ thống quản lý phiên bản như Git; (2) Build stage: ứng dụng được biên dịch/build từ source code; (3) Test stage: các test tự động chạy để kiểm tra tính đúng đắn của code; (4) Deploy stage: ứng dụng được deploy lên môi trường staging hoặc production. Ví dụ thực tế: developer push code lên GitHub, GitHub Actions kích hoạt workflow build ứng dụng, chạy unit test và integration test, nếu pass thì deploy lên staging, sau đó một thành viên review và phê duyệt trước khi deploy lên production.

**Theo ITviec** (chia sẻ từ anh Nguyễn Trường Giang – Mobile Tech Lead tại Amanotes), quy trình gồm 2 workflow chính:
- **Development:** khi developer phát triển tính năng, họ tạo branch riêng, tạo pull request để merge vào nhánh development chung; lúc này CI/CD tự động chạy build, test, lint check và report kết quả.
- **Deployment:** khi pull request được merge, hệ thống build sản phẩm rồi upload lên TestFlight (iOS) hoặc Fire App Distribution (Android); khi upload xong sẽ có thông báo qua Slack để team QC vào tải bản build và test thủ công.

Bài ITviec cũng mô tả cơ chế hoạt động: khi developer tạo thay đổi trên Git repository (ví dụ tạo pull request), Git repository sẽ gửi thông báo đến CI/CD tool, tool này tự động thực hiện các thao tác đã cài đặt sẵn, rồi cập nhật kết quả ngược lại cho Git repository biết pull request có pass hết các bước (bao gồm testing) hay không — nhờ đó reviewer chỉ cần nhìn trạng thái passed/failed để đánh giá chất lượng.

### 1.3 Ưu điểm và nhược điểm của CI/CD

**Ưu điểm (theo ITviec):**
- Tránh lỗi không đáng có (lỗi compile, lỗi môi trường build khác nhau giữa các máy)
- Đảm bảo logic — tính năng mới không phá vỡ tính năng cũ (nhờ automation test)
- Giúp developer tập trung vào code, không phải tự build/deploy thủ công
- Nâng cao chất lượng code qua các ràng buộc (VD: giới hạn quy mô pull request)
- Phát triển kỹ năng viết unit test cho developer (qua chỉ số code coverage)
- Tối ưu tốc độ phát triển sản phẩm nhờ theo dõi build pipeline

**Ưu điểm (theo Milan):** CI/CD pipeline giúp cải thiện sự cộng tác, chất lượng code, và hệ thống trở nên linh hoạt, đáng tin cậy hơn.

**Nhược điểm (theo ITviec):**
- Nhiều pull request cùng lúc → phải chờ merge, update lại code khi conflict, test lại từ đầu → gián đoạn tiến độ
- Phụ thuộc vào dịch vụ CI/CD bên thứ 3 — nếu dịch vụ gặp sự cố/ngừng hoạt động thì dự án bị ảnh hưởng nghiêm trọng

### 1.4 Khi nào nên dùng và khi nào không nên dùng CI/CD

**Theo ITviec:** Nên áp dụng CI/CD càng sớm càng tốt, kể cả với dự án cá nhân (có thể dùng dịch vụ miễn phí), vì quy trình tốt giúp chất lượng công việc tối ưu hơn. Tuy nhiên, cân nhắc **chưa** dùng khi: tổ chức không có người đủ khả năng vận hành CI/CD, developer chưa nắm rõ về tool, hoặc chưa biết cách đảm bảo quy trình — vì nếu có sự cố mà không đủ chuyên môn xử lý sẽ gây gián đoạn và tốn nhiều thời gian.

## 3. Các yếu tố so sánh các công cụ

**Theo Milan**, khi chọn nền tảng CI/CD nên cân nhắc:
1. **Cloud-based vs. self-hosted** — nền tảng cloud-based thường có sẵn UI quản lý pipeline và không cần cài đặt/bảo trì, còn self-hosted cho phép tự quyết định nơi đặt build server/agent
2. **Tính dễ dùng** — giao diện thân thiện, tài liệu rõ ràng
3. **Khả năng tích hợp** — tích hợp liền mạch với ngôn ngữ lập trình, công cụ quản lý mã nguồn, issue-tracking và nền tảng cloud đang dùng
4. **Khả năng cấu hình** — từ trigger khởi chạy pipeline đến cách xử lý khi build/test thất bại, có thể cấu hình qua script hoặc UI
5. **Mức độ hiểu biết của đội ngũ về nền tảng** — cần xét xem kỹ sư có kinh nghiệm với nền tảng đó không, và tài liệu hỗ trợ có đầy đủ không

## 1. Khái niệm Test Harness

**Theo FMIT:** Test harness là một bộ công cụ dùng trong kiểm thử phần mềm để điều khiển và tự động hóa các bài kiểm thử, bao gồm các thành phần như môi trường kiểm thử, công cụ giám sát, dữ liệu kiểm thử và script để thực hiện/theo dõi kết quả kiểm thử. Nó giúp tự động hóa quá trình kiểm thử, tăng khả năng kiểm tra và giảm sự can thiệp của con người. Ví dụ minh họa: trong một ứng dụng thương mại điện tử, test harness có thể tự động kiểm thử các chức năng như thanh toán, giỏ hàng, quản lý đơn hàng.

**Theo Tutorialspoint:** Test harness giống một testing framework — là tập hợp phần mềm, input được tạo ra để kiểm tra một phần mềm trong nhiều môi trường khác nhau rồi phân tích kết quả, chủ yếu hỗ trợ integration testing. Nó gồm các stub, driver và công cụ automation/debugging, cung cấp bản sao tài nguyên/cấu hình chưa có sẵn trong môi trường test (ví dụ hệ thống PHP chưa triển khai xong thì dùng test harness thay thế).

## 7. Test Harness vs Test Framework

Test harness không có tính năng record & play, còn phạm vi Test framework rộng hơn (data-driven, keyword-driven, hybrid...).
